1. System Overview — Two Four-GPU Pools

Why separate-async: the dedicated blue pool keeps producing while the green pool trains, so generation and optimization overlap without time-sharing the same four GPUs. The code still constructs hybrid vLLM replicas on trainer GPUs, but enable_switch=false means they are reclaimed at step start and are not used as burst capacity during training.

3. Streaming Dataflow — 64 Prompt Groups, 16 Samples + One Baseline

Transmission unit: ReplayBuffer selects prompt UUIDs, then materializes every successful sampled trajectory under those UUIDs. A nominal batch therefore contains 64 groups × 16 trainable responses = 1,024 trajectories; the 64 greedy generations only provide scalar baselines and are deleted before training.

4. One Source Row, Two Model Representations

Critical distinction: the dataset’s input_ids[1024], attention mask, position IDs, and processor audio tensors make each singleton dataloader item structurally collatable, but vLLM does not simply consume that padded tensor. The agent loop passes the structured messages, pre-rendered full_prompt_text, and raw audio so vLLM can tokenize model-specific audio placeholders. After generation, training tensors are rebuilt from the final prompt and response token IDs, with multimodal features aligned to that final sequence.

Dataset item 8 loader workers

raw_prompt = structured chat messages full_prompt_text = rendered chat + generation marker multi_modal_data = {audio: [(waveform, sample_rate)]} input_ids = left-padded/truncated to 1024 multi_modal_inputs = processor audio tensors

Why keep both forms? agent loop

  • Generation needs raw audio and exact rendered text understood by vLLM’s multimodal tokenizer.
  • Training needs token-aligned masks, log-probs, reward, and audio features for the exact sampled response.
  • Rebuilding after generation prevents stale dataset padding from defining the final HF sequence layout.

5. vLLM Batching — Async Requests, Not a Fixed 64×17 Tensor

What “batched” means for vLLM: 1,088 is the run-wide nominal request count, not one dense model batch. Eight CPU agent-loop actors asynchronously issue requests into a global four-replica service. Each vLLM engine continuously admits, preempts, prefills, and decodes up to 16 active sequences under a 28,672-token scheduler ceiling; completed slots can be refilled immediately. The one greedy baseline for a prompt is deliberately dependent on completion of that prompt’s 16 sampled sessions.

6. HF/FSDP2 Batching — Prompt Groups Become Token-Budgeted Micro-Batches

What “batched” means for HF/FSDP2: prompt groups are only a replay-selection concept. Once 64 complete groups are chosen, the trainer works on 1,024 independent sampled trajectories. It reorders them into four equal-count, token-balanced rank shards. Each rank receives 256 jagged rows as one local mini-batch, then dynamically forms gradient-accumulation micro-batches whose summed sequence length fits the 3,072-token/GPU budget. The configured ppo_micro_batch_size_per_gpu=4 is the fixed-size fallback and does not determine the active dynamic pack size.

A · Submit and sample controller

prepare_step(): submit 64 new prompts ReplayBufferAsync.sample(step, "train", 64) evict stale / failed terminal groups refill one-for-one choose oldest eligible groups

B · Balance controller

  • Materialize all trajectories for the selected prompt UUIDs.
  • Pad only as required for downstream divisibility.
  • Partition by sequence workload across four data-parallel ranks.

C · π-old in bypass mode FSDP2 ×4

rollout_correction.bypass_mode = true old_log_probs := rollout_log_probs # no actor recompute # no token-IS correction stage

D · ReMax advantage controller

returns = reverse_cumsum(rm_scores * response_mask) advantage = returns - greedy_baseline advantage *= adv_scale[data_source] # openml=1.0; binary_adv=false

E · Actor update trainer pool

  • One PPO epoch; global mini-batch is 64 × 16 = 1024 trajectories.
  • Four ranks receive 256 trajectories each, then form variable-size micro-batches capped at 3072 sequence tokens/GPU.
  • Token-mean clipped PPO loss; no entropy bonus and no KL loss.

F · Commit policy version NCCL

  • Actor advances one policy version.
  • Standalone rollout is refreshed at every on_step_end().
  • Metrics preserve each trajectory’s minimum/maximum generation version.

9. Parameter Synchronization — One Mandatory Training-Time Path

Why abort rather than drain: a hard drain would turn every policy commit into a generation barrier. The fully asynchronous client retains partial output and can continue after the manager restores KV capacity and resumes replicas. LoRA adapter-only fast sync is not enabled here, so the legacy merged/full-weight NCCL path is used despite rank-32 LoRA training.

10. Backpressure and Freshness — Prompt-Age Budget of Eight Versions

Producer depth warmup + refill

  • One 64-prompt batch is submitted before the loop.
  • Each step submits another 64 before sampling.
  • Failed or evicted groups receive exact one-for-one replacement prompts.

Drop policy ReplayBufferAsync

  • Threshold: eight policy versions.
  • A finished group is stale when step − prompt_step + 1 > 8.
  • Stale and failed terminal groups are cleared and refilled before selection.

Consumer blocking 2 s polling

  • The controller waits until 64 eligible groups exist.
  • Generation actors continue independently while the controller polls.
  • Oldest prompt versions are selected first to limit further aging.

Trajectory observability version tags

  • min_global_steps and max_global_steps capture cross-sync continuation.
  • Metrics report both policy lag and within-trajectory version span.
  • Bypass mode trusts the rollout policy log-prob actually stored with each token.

Architectural reading: “separate async” is the essential choice; “hybrid switch disabled” is equally important. Training uses a stable 4+4 split with continuous production, while the hybrid engines exist primarily to make validation use otherwise-idle trainer GPUs.
