1. System Overview — Single Controller, Lock-Step GPU Ranks

“SPMD” here means rollout execution: each GPU rank runs the same synchronous generation method over its shard. The broader trainer is a single-controller, stage-by-stage Ray program—not a queue-driven producer/consumer pipeline.

3. Synchronous Rollout — One Complete Batch at a Time

Scheduling unit: a full generation batch. There is no TransferQueue, replay buffer, prompt-group freshness budget, or independent producer. Generation itself may batch requests inside vLLM, but the trainer cannot advance until the distributed call returns.

4. Per-Step Pipeline — A Chain of Global Barriers

Throughput implication: rank skew and long-tail responses create bubbles because each phase is a global completion point. The design favors deterministic freshness and simple ownership over overlap; no universal performance ratio is asserted here.

A · Rollout SPMD GPUs

  • All ranks enter generate_sequences().
  • Fresh actor weights load into each local vLLM engine.
  • Every rank returns before reward processing starts.

B · Score and anchor blocking RPCs

  • Reward model/rule function produces token scores.
  • Actor recomputes old log-prob; reference computes KL anchor.
  • Critic values are optional by estimator.

C · Advantage controller

scores → optional KL penalty → rewards values + rewards → GAE / GRPO / ReMax balance tokens across data-parallel ranks

D · Optimize trainer GPUs

  • Update critic first when enabled.
  • Update actor after critic warmup.
  • The next rollout transition exports the updated actor.

5. Hybrid GPU State Machine — Rollout and Training Time-Share Memory

No concurrent same-GPU execution: the hybrid worker explicitly changes personality. With free_cache_engine=true, release() sleeps vLLM and frees weights/KV cache so training state can occupy the GPU.

6. Parameter Synchronization — Per-Rollout In-Process Reload

The rollout model does not alias actor tensors. On every synchronous hybrid rollout entry, actor parameters are materialized/iterated and loaded into the local vLLM model. LoRA uses an adapter request path; full weights use vLLM’s model loader. This is local to each colocated rank—not the newer disaggregated checkpoint-engine protocol.

7. Freshness, Backpressure, and Failure Semantics

Exact step freshness zero staleness

  • One training batch is generated, scored, and consumed before the next begins.
  • The actor cannot update while that batch is still generating.
  • Next-step rollout loads the actor produced by the previous completed update.

Implicit backpressure driver barrier

  • No explicit queue capacity or freshness threshold exists.
  • The blocking generate_sequences() call is the backpressure mechanism.
  • Slow ranks and long responses hold the entire controller at the barrier.

No partial preservation batch boundary

  • Rollouts finish before training takes GPU ownership.
  • There is no replay buffer carrying partial trajectories across policy versions.
  • Failure handling belongs to the synchronous RPC/job path, not a retrying prompt state machine.

Deterministic ownership hybrid engine

  • vLLM owns rollout memory only during generation.
  • FSDP/Megatron owns training memory after release.
  • The explicit transition avoids actor/rollout compute races on colocated GPUs.
